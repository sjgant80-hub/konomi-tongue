One lossless codec every organ speaks between themselves. What it isA language the organs already half-know

Compression is prediction: the better you can guess the next byte, the fewer bits you spend on it. LIGHT is a coder that guesses from what it has seen, primed before the first byte with a dictionary grown from the estate's own files — the headings, the record shapes, the credit lines the estate writes again and again. A message both sides already partly know is cheap; that is what it means for two organs to "speak the same language", measured in bytes.

  • One codec, everywhere inside. The same codec.mjs in every organ that speaks it: the memory on disk, the records a node keeps, the messages organs send each other. Standard forms (JSON, text, what a human reads) appear only at the edges.
  • Signed packets, checked before decode. An organ-to-organ message is a LIGHT packet carrying an Ed25519 signature. The door checks size, format, the pinned sender, the signature and a replay counter on the raw bytes, and only then decodes the body. Bytes from someone without the key never reach the decoder.
  • Many files as one vault. A whole store — the memory, a folder of records — packs into one solid LIGHT stream, so what the files share is paid for once, and every file's SHA-256 is checked on the way out.
  • Honest about the number. The spec set 15× denser than JSON. It is not 15×; on 179 held-out files the median is 3.4×. That claim is kept, failed, with the measured number — below. So is the speed claim, which also failed.

How it worksInside everything, standard at the edges

  1. Store in LIGHT. An organ writes its memory and records through the codec. On disk they are LIGHT; the file a human reads is produced at the edge when asked.
  2. Talk in LIGHT. An organ-to-organ message is a signed LIGHT packet. The receiver's door checks it on raw bytes and decodes the body only if it is admitted.
  3. The dictionary is the shared tongue. Grown from TRAIN files only and versioned. Both sides hold it, so a short familiar message codes to very little. A later version grows from later files; the id in each packet says which dictionary it needs.
  4. Translate only at the edges. Where the estate meets a human, a standard API or a browser, a thin edge codec turns LIGHT into the standard form and back. Inside is all LIGHT; the outside never needs to know it exists.

The language barrier, honestlyWhat a private language does and doesn't do

Bytes meant to break software are written in languages an attacker shares with an ordinary target — SQL, script, shell, a template. A LIGHT door does not speak them: sent as raw bytes they fail at the size or the magic number, before anything parses them. But that is only true at the door. The same bytes carried as data inside a signed packet decode back to exactly themselves — LIGHT does not disarm them; only the edge that renders or runs that data can. This demo shows both, in your browser, on the sealed test inputs; the same claims measured in Node are in the receipts above (B1–B3).

Honest scopeDefense-in-depth, not magic

The hard floor is the signature. A LIGHT packet is refused unless it is signed by a pinned key, checked on raw bytes before any decode. No cleverness and no volume forges a signature without the key. That is what protects an organ-to-organ channel.

The language is the layer on top. Because LIGHT is custom, compressed and evolving, the shared-language attack surface at a door is absent — standard exploits are bytes in a language it does not speak. Real and useful, but it is surface-elimination, not a substitute for the signature, and it is not security-through-obscurity standing alone.

It does not disarm data. Injection carried as the content of a message is decoded faithfully; the edge that renders or executes it is where it is made safe (escaped, parameterised). LIGHT moves the bytes; it does not sanitise them.

It is not encryption. LIGHT makes data smaller and proves who sent it; it does not hide it. Anyone holding the dictionary can decode a body. Confidentiality comes from encryption in transit and at rest, alongside LIGHT.

Out of scope, stated plainly. A stolen key (the holder of a key is that sender), host or root compromise, and physical or social attacks are not addressed here. LIGHT removes the shared-language and unsigned-message vectors, not every conceivable one. The edges — where LIGHT meets a standard form — are the one place the shared-language surface briefly exists, so the edge codec is itself verify-first and gated.

The broader claim that a private verified language "neutralises an AI swarm" is a framing, not something this page measures. What is measured is above: the codec, the door, the vault, on held-out files, with the failures kept.

Against what you use now

The standard coders are free, so the honest comparison is bytes, on the same 179 held-out files: LIGHT 318,550 B, Brotli 11 326,952 B, gzip −9 408,024 B, from 1,952,051 B raw. On small messages of up to 2 KB — the size of an organ-to-organ message — the median is LIGHT 430 B, Brotli 475 B, gzip 575.5 B, and LIGHT is smaller than both on 42 of 44. The win over a standard coder is small on big files and real on small messages, which is what systems mostly send each other. What no standard coder gives you is the door: a signature checked on raw bytes before anything is parsed.

Security and data protection

  • Where the data is. On your machines. The kernels do no I/O, read no clock and call no network; this page requests only its own files under a self-only content security policy.
  • Who sent it. Ed25519 signatures over a fixed domain, the header and the body; senders pinned by key; a counter that refuses replays and reordering; all checked on the raw bytes, and the decoder is never called for a refused packet.
  • Keys. LIGHT neither makes nor stores keys: your door supplies the pinned public key for each sender and the verify function, so private keys stay in the key store you already run.
  • Bounded before it is read. A packet is at most 1 MiB and a body may claim at most 4 MiB by default (you can set lower), both checked before decoding; and because the signature is checked first, a sender without a pinned key cannot make you spend any decode time at all.
  • Whether it changed. The codec stores a 4-byte check of the input and returns the exact bytes or nothing; the vault stores each file's SHA-256 and refuses the whole vault if one differs; vault paths cannot reach outside their folder.
  • Personal data (UK GDPR). LIGHT is neither anonymisation nor encryption: personal data in LIGHT is still personal data, and your controller duties are unchanged. A dictionary grown from your files holds fragments of them — treat it with the same care as the files it was grown from, and share it only with systems allowed to read them.
  • Assurance you can re-run. The source is MIT and open; the tests, the receipts and the mutation gate run on GitHub's runner on every push, and on your own machine with the commands in Start here.

Risks, answered straight

  • It is slow. 0.369 MB/s encoding and 0.366 MB/s decoding on one thread of the laptop that measured it — it failed its own 0.5 MB/s bar, and the claim is kept failed. Use it where messages are small or where you can spread the work across cores; the cost case counts the CPU.
  • It is not 15×. The median held-out file is 3.4× smaller. Most of a new file is new information, and a dictionary only saves what recurs.
  • If you already compress, the bill barely moves. Against Brotli the total saving on the held-out files was 2.6%.
  • The dictionary is a dependency. Lose it and you cannot decode what was written with it. Its id is in every packet and vault; keep every version you ever wrote with, beside the data.
  • The format is versioned and frozen. A change to the model is a new version (the tests pin the exact output bytes); old versions must stay readable.
  • It is young. In the estate, 5 public repositories speak it in their own code and 95 more carry it only through a copy of the kit (fall-kit's census v2, which counts own code only: light/vendor/fall-kit/core/receipts/phase2.json, vendored byte for byte). The first channel was break-it's immune mesh, where a 64-antigen share went from 11,667 B as JSON to 4,669 B as LIGHT. Start with one channel, as it did.
  • It does not stop a stolen key, and it is not encryption. See honest scope.
  • No independent security review yet. No outside party has audited the codec or the door. The assurance is what you can re-run yourself — the tests, the receipts, the barrier claims and the mutation gate — so commission your own review before LIGHT carries anything sensitive.

LIGHT is a small, owned piece of infrastructure: one internal format whose messages are signed and checked before anything reads them, and whose stores are lossless and hash-checked. AdoptionHow a team rolls it out

LIGHT fits a team that runs many services, agents or devices exchanging structured messages and keeping records — where the same shapes recur, where it matters who sent a message, and where the data has to stay in-house. It is not for bulk data you already compress where CPU is tight, and it does not replace encryption.

  1. Try it on your own data, here. Paste one of your real records into Try it. Nothing leaves the tab.
  2. Run the gates on your own machine. Clone the repository and run the commands in Start here, and the mutation gate as light.yml runs it. You are trusting what you just re-ran, not this page.
  3. Grow your own dictionary from your own files. Split your files by date into TRAIN and HELD-OUT; grow the dictionary from TRAIN only (light/tools/dict.mjs is the method). Version it.
  4. Write down what you expect before you measure. Commit your claims first, as light/claims.json was, then measure on HELD-OUT with the judge and the check tool. Keep what fails.
  5. Wire one channel, backwards-compatible. Make the receiver accept LIGHT packets and the old format; switch the sender when both ends speak LIGHT. break-it's mesh did exactly this: a JSON share from an older node still adopts.
  6. Turn on the door. Pin each sender's key, keep each sender's last counter, refuse anything unsigned. Decode only what the door admits.
  7. Gate it in your CI. Copy .github/workflows/light.yml: the tests, the receipt checks and the pinned mutation gate, with the memory cap.
  8. Keep the dictionaries with the data. Every packet and vault names the dictionary it needs; retire none you ever wrote with.

What success looks like: on your own held-out files, the bytes against your baseline, measured; on the channel, nothing decoded before it was verified; in CI, every kernel clean on every push.

White paperLIGHT: prediction as a shared language, behind a verify-first door

Abstract

LIGHT is a lossless, integer-only, context-mixing arithmetic coder primed with a dictionary grown from an organisation's own files, wrapped in a signed packet whose door verifies sender, signature and counter on the raw bytes before decoding. Measured on 179 held-out files with 19 claims sealed in git before any code existed, it compressed the median file 3.4×, stayed lossless throughout, beat both gzip −9 and Brotli 11 on 42 of 44 small messages, packed a 356-file memory 4.162× byte-identically, and refused every one of 28 sealed test inputs sent as raw bytes and 4 forgeries without decoding any. It failed its 15× target and its 0.5 MB/s speed target; both failures are kept.

1 · Prediction is compression

An arithmetic coder spends close to −log₂ p bits on a bit it predicted with probability p. LIGHT predicts each bit from seven contexts — the bit's place in its byte, the last one to four bytes, the current word, and a match model that finds where the last six bytes appeared before and predicts what followed them — and mixes the seven guesses with weights that learn as they go. The mixed probability, a 12-bit integer, splits a 32-bit range. No floating point is used anywhere, so an encoder in Node and a decoder in a browser make the same prediction for every bit.

2 · A language both sides hold

Before the first byte, the model reads a shared dictionary — 182,969 bytes of the lines the estate writes again and again, grown from TRAIN files only. That primes both its tables and its match history, so a short message made of familiar pieces codes to very little. Copying the primed tables per message would cost megabytes; instead a short message is lent the tables, the first write to each slot is journaled, and the journal hands the model back byte-identical before encode or decode returns (tested by hashing the whole model before and after).

3 · The door

A LIGHT packet is a 23-byte header, the coded body and a 64-byte Ed25519 signature over a fixed domain, the header and the body. The door checks, in order and on the raw bytes: size, magic, version, length, dictionary, sender, signature, counter — and only then decodes. Bytes in any other language fail at size or magic; bytes in LIGHT's own format from someone without a pinned key fail at sender or signature; the decoder is never called for either. Data carried inside an admitted packet comes back exactly, so the edge that shows or runs it remains responsible for making it safe.

4 · Method

The claims and the barrier corpus were committed (ac90c1e) before the codec, the door or any measuring code. Material is every git-tracked JSON and Markdown file of up to 256 KB in the estate's public clones, split by last-commit date into TRAIN and HELD-OUT; the dictionary and every tuning choice read TRAIN only. A pure judge, itself mutation-gated, holds each claim against the measured facts; CI re-runs the judge on the receipt's own facts, re-checks every seal, measures the barrier claims again and runs the mutation gate over every kernel on GitHub's runner.

5 · Results

Median 3.416× over 179 held-out files (L1, 15×: failed, as predicted). 0 round-trip failures (L2). Small messages: median 430 B against Brotli's 475 B and gzip's 575.5 B (L3). Totals: 318,550 B against Brotli's 326,952 B (L4). Speed: 0.369 MB/s encode, 0.366 MB/s decode on one thread (L5: failed). Memory: 356 files, 3,009,962 B to 723,167 B, 4.162×, byte-identical (M1, M2). Mesh: a 64-antigen share 2.499× smaller than its JSON, forgeries refused before decode (K1–K3). Barrier: B1–B3 held. The mutation gate: 336 of 351 mutants killed, 15 reviewed-equivalent with written reasons.

6 · Limits

A shared dictionary saves only what recurs, so new material will not reach 15×. One thread is slow. Against data already Brotli-compressed the gain is small. The dictionary is a versioned dependency that must be kept with the data. The model-facing claims (T1, T2) were not measured in the receipt. LIGHT is not encryption and does not address a stolen key.
