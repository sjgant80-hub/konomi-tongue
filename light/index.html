What it isA language the organs already half-know

Compression is prediction: the better you can guess the next byte, the fewer bits you spend on it. LIGHT is a coder that guesses from what it has seen, primed before the first byte with a dictionary grown from the estate's own files — the headings, the record shapes, the credit lines the estate writes again and again. A message both sides already partly know is cheap; that is what it means for two organs to "speak the same language", measured in bytes.

  • One codec, everywhere inside. The same codec.mjs in every organ: the memory on disk, the records a node keeps, the messages organs send each other. Standard forms (JSON, text, what a human reads) appear only at the edges.
  • Signed packets, checked before decode. An organ-to-organ message is a LIGHT packet carrying a signature. The door checks size, format, the pinned sender and the signature on the raw bytes, and only then decodes the body. Bytes from someone without the key never reach the decoder.
  • Many files as one vault. A whole store — the memory, a folder of records — packs into one solid LIGHT stream, so what the files share is paid for once, and every file's hash is checked on the way out.
  • Honest about the number. The spec set 15× denser than JSON. It is not 15×; on held-out files it is about 3.5×. That claim is kept, failed, with the measured number — below.

How it worksInside everything, standard at the edges

  1. Store in LIGHT. An organ writes its memory and records through the codec. On disk they are LIGHT; the file a human reads is produced at the edge when asked.
  2. Talk in LIGHT. An organ-to-organ message is a signed LIGHT packet. The receiver's door checks it on raw bytes and decodes the body only if it is admitted.
  3. The dictionary is the shared tongue. Grown from TRAIN files only and versioned. Both sides hold it, so a short familiar message codes to very little. A later version grows from later files; the id in each packet says which dictionary it needs.
  4. Translate only at the edges. Where the estate meets a human, a standard API or a browser, a thin edge codec turns LIGHT into the standard form and back. Inside is all LIGHT; the outside never needs to know it exists.

BlueprintFour kernels, each gated

Each is a pure kernel with its own tests, under a mutation gate: the gate changes the code one operator at a time and the tests must catch every change. Survivors are allowed only with a written reason. CI runs all of it.

The language barrier, honestlyWhat a private language does and doesn't do

Bytes meant to break software are written in languages an attacker shares with an ordinary target — SQL, script, shell, a template. A LIGHT door does not speak them: sent as raw bytes they fail at the magic number, before anything parses them. But that is only true at the door. The same bytes carried as data inside a signed packet decode back to exactly themselves — LIGHT does not disarm them; only the edge that renders or runs that data can. Honest scopeDefense-in-depth, not magic

The hard floor is the signature. A LIGHT packet is refused unless it is signed by a pinned key, checked on raw bytes before any decode. No cleverness and no volume forges a signature without the key. That is what protects an organ-to-organ channel.

The language is the layer on top. Because LIGHT is custom, compressed and evolving, the shared-language attack surface at a door is absent — standard exploits are bytes in a language it does not speak. Real and useful, but it is surface-elimination, not a substitute for the signature, and it is not security-through-obscurity standing alone.

It does not disarm data. Injection carried as the content of a message is decoded faithfully; the edge that renders or executes it is where it is made safe (escaped, parameterised). LIGHT moves the bytes; it does not sanitise them.

Out of scope, stated plainly. A stolen key (the holder of a key is that sender), host or root compromise, and physical or social attacks are not addressed here. LIGHT removes the shared-language and unsigned-message vectors, not every conceivable one. The edges — where LIGHT meets a standard form — are the one place the shared-language surface briefly exists, so the edge codec is itself verify-first and gated.

The broader claim that a private verified language "neutralises an AI swarm" is a framing, not something this page measures. What is measured is above: the codec, the door, the vault, on held-out files, with the failures kept.

FAQQuestions

What is LIGHT?
One lossless codec the estate's organs use to store and exchange their data. It is a context-mixing arithmetic coder primed with a shared dictionary grown from the estate's own files, so a message both sides partly know costs few bytes. Memory, organ-to-organ messages and records are carried in LIGHT; it translates to JSON or text only at the edges where the estate meets the outside world.
Did it reach 15× denser than JSON?
No, and that was predicted. On held-out estate files the median was about 3.5× smaller than the committed file, not 15×. A shared-dictionary coder saves what recurs; most of a new file is new. The claim was sealed as the bar and is kept FAILED with the measured number.
Is LIGHT a security system?
The security is the cryptographic part: a LIGHT packet is refused unless it is signed by a pinned key, on the raw bytes, before anything is decoded. That is the hard floor. The custom, compressed, evolving language removes the shared-language attack surface on top of that — real, but defense-in-depth, not a substitute for the signature. It does not make injection carried as data safe; only the edge that renders or runs that data can.
How is it measured honestly?
Every claim was committed to git before the codec or any measuring code existed. Files are split TRAIN/HELD-OUT by their last commit date; the dictionary and all tuning read TRAIN only, and the measurement reads HELD-OUT for the first time. A pure, gated judge holds each claim against what was measured; failures are kept on the page.
